# Test vectors

Every file here is generated and committed. Generators live in `generate/`. Nothing in this
directory should be edited by hand: a hand-tuned expectation is how a test ends up asserting the
implementation's own bug back at itself.

| File | Generated by | Asserted by |
| --- | --- | --- |
| `bip-derivation.json` | `generate/bip-vectors.py` | `crates/kernel/tests/official_vectors.rs` |
| `registry-addresses.json` | `generate/address-vectors.mjs` | `crates/kernel/tests/registry_addresses.rs` |
| `cosmos-signing.json` | `generate/generate.mjs` | `crates/cosmos/tests/golden_vectors.rs` |
| `evm-signing.json` | `generate/evm-vectors.mjs` | `crates/evm/tests/golden_vectors.rs` |
| `svm-signing.json` | `generate/svm-vectors.mjs` | `crates/svm/tests/golden_vectors.rs` |
| `keyring-envelope.json` | `crates/kernel/examples/seal_fixture.rs` | `crates/kernel/tests/keyring_envelope.rs` |

## What each set is for

**`bip-derivation.json`** holds the official BIP-39, BIP-32 and SLIP-0010 vectors, fetched from
their normative upstreams rather than transcribed. 24 BIP-39 English cases, the four seed-based
BIP-32 vectors (17 derived keys), and both SLIP-0010 ed25519 vectors (12 derived keys). These
prove the derivation maths is right.

**`registry-addresses.json`** holds one case per distinct (coin type, bech32 prefix, address
scheme) combination in `zunia-chain-registry`: 241 combinations across 332 chains, 26 coin
types, 50 of them Ethermint. These prove Zunia applies that maths with the parameters the
registry actually supplies. The BIP vectors cannot catch a wrong coin type or a missed Ethermint
flag, and either produces a valid address belonging to nobody.

**`cosmos-signing.json`** holds `SIGN_MODE_DIRECT` and `SIGN_MODE_LEGACY_AMINO_JSON` sign bytes
for ten message types plus three ADR-36 cases, generated with CosmJS. Asserted byte for byte.
Cosmos signs bytes, so anything short of byte equality proves nothing: a one-byte difference
yields a signature that verifies against nothing, and the chain reports it as `unauthorized`
with no hint that the encoding was at fault. This set has already caught one such bug, an
omitted non-nullable `timeout_height` in `MsgTransfer`.

**`evm-signing.json`** holds eight transactions (legacy, EIP-2930, EIP-1559, contract creation,
a chain id large enough to break a 32-bit `v`, and zero-valued fee and amount fields), eight
`personal_sign` messages, and five EIP-712 documents, generated with ethers v6. Every EIP-712
case is asserted at each intermediate step: `encodeType`, `typeHash`, `domainSeparator`,
`hashStruct`, `encodeData` and only then the digest, because a mismatch in the final hash alone
does not say which member was misencoded. The spec's own Mail example is included, so the
published intermediate hashes apply and the chain of assertions is anchored to the specification
rather than only to ethers. Note that ethers' `signature.v` is normalised to 27 or 28 and is not
the byte on the wire, and its `encodeData` is the spec's `typeHash || encodeData`; both are
recorded under names that say what they contain.

**`svm-signing.json`** holds nine Solana transactions generated with `@solana/web3.js`, covering
transfers at zero, one and a whole SOL, multiple instructions, a second signer, undecodable
programs, and instruction data long enough to force a two-byte compact length. One divergence is
recorded rather than hidden: web3.js orders accounts within a privilege class by base58 string
while solana-sdk and this crate order by raw key bytes. Both are valid on chain since indices are
self-consistent either way, so each case carries an `orderingsAgree` flag and byte equality is
asserted only where the two agree. All nine currently agree.

**`keyring-envelope.json`** is a wallet sealed by a known-good build. It proves a later build can
still open it. If that test fails, the format changed and every existing wallet became
unopenable, which needs a migration and an `ENVELOPE_VERSION` bump, not a regenerated fixture.

## Regenerating

```bash
# Official BIP vectors. Needs network and the gh CLI.
python3 generate/bip-vectors.py

# JavaScript-reference vectors. Needs the sibling zunia-chain-registry checkout.
cd generate && pnpm install
pnpm generate:all

# Or individually.
node generate.mjs          # Cosmos, via CosmJS
node address-vectors.mjs   # per-chain addresses, via CosmJS
node evm-vectors.mjs       # Ethereum, via ethers v6
node svm-vectors.mjs       # Solana, via @solana/web3.js

# The pinned envelope. See the warning above before doing this.
cargo run -p zunia-kernel --example seal_fixture > keyring-envelope.json
```

Then read the diff. For the official BIP vectors a change means an upstream edited a finalised
specification, which should never happen. For the JavaScript-derived vectors it means either the
reference library changed its encoding or the registry changed, and both need a human to decide
which side is right. CI regenerates these and fails on any diff, so a silent drift cannot merge.

## Fuzzing

Property-based coverage of the same parsers lives in `../../fuzz`. The vectors prove the
implementation is right on inputs we thought of; the fuzz targets cover the ones we did not. Both
EIP-712 documents and Solana messages here double as fuzz corpus seeds, which is how two
misrepresentation bugs were found. See `../../fuzz/README.md`.
